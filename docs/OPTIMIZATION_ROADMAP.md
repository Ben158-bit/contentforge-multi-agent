# ContentForge 优化路线图

本文档针对项目评估中相对较低的四项：可扩展性、评测与科学性、生产部署能力、GitHub 展示与社区成熟度。

## 1. 当前判断

ContentForge 已经是一个完成度较高的垂直应用型 MVP：它有完整的营销内容流水线、人工确认、阶段编辑、反馈学习、SQLite checkpoint、SSE、Docker、CI 和较完整的测试。

当前短板不是“缺少更多 Agent”，而是以下能力还没有被工程或数据充分证明：

- 新增流程和模型时需要修改核心代码；
- 只能证明流程可运行，不能量化证明输出质量持续提升；
- 单进程 SQLite 架构不适合多实例和长时间生产运行；
- GitHub 页面还没有把功能、证据和限制展示到足够专业的程度。

## 2. 优先级总览

| 优先级 | 目标 | 主要结果 |
|---|---|---|
| P0 | 建立可信的质量证据 | 评测集、评分标准、回归门槛、可复现实验 |
| P0 | 降低运行时耦合 | Provider 接口、流程定义、配置化节点 |
| P1 | 提升生产可靠性 | 队列、持久化事件、分布式限流、可观测性 |
| P1 | 提升公开仓库可信度 | 截图、Demo、徽章、发布说明、限制说明 |
| P2 | 形成可扩展生态 | 插件机制、模板市场、模型路由、贡献流程 |

## 3. 可扩展性

### 3.1 现状与问题

当前流程是固定的 `research → competitor → strategy → copywriting → review → human_confirm`。这对营销内容 MVP 是合理的，但当需求扩展到邮件、广告、SEO、视频脚本或品牌合规时，新增能力会直接进入图编排、状态结构和前端判断逻辑，修改成本较高。

### 3.2 建议方案

#### P0：抽象 Provider 边界

定义稳定的协议，而不是让节点依赖具体实现：

```python
class LLMProvider(Protocol):
    def generate(self, request: LLMRequest) -> LLMResponse: ...

class SearchProvider(Protocol):
    def search(self, request: SearchRequest) -> SearchResponse: ...
```

至少提供 `DeepSeekProvider`、`FakeProvider` 和一个可测试的 `FailingProvider`。节点只依赖协议，配置决定实际实现。

验收标准：

- 不修改 Agent 节点代码即可切换 FakeLLM、DeepSeek 和第二个兼容 OpenAI API 的模型；
- Provider 单元测试覆盖超时、空响应、无效 JSON、重试和成本统计；
- README 有 Provider 扩展示例。

#### P0：把流程定义从业务代码中抽出来

将节点顺序、输入输出契约、是否需要人工确认、失败重试策略放入版本化 YAML/JSON 或 Python 配置对象。核心图只负责解释流程定义，不负责硬编码所有营销阶段。

建议每个节点声明：

- `id`、`role`、`prompt_template`；
- `input_schema`、`output_schema`；
- `on_success`、`on_failure`、`max_retries`；
- `human_gate` 和可编辑字段。

验收标准：新增一个“SEO 改写”节点只需新增配置、Prompt 和 schema，不修改 runner、API 主流程和前端核心组件。

#### P1：稳定交接契约

为每个阶段使用版本化 Pydantic schema，并在 checkpoint 中保存 `pipeline_version`、`node_version` 和 schema 版本。这样可以避免 Prompt 或字段升级后无法恢复旧任务。

#### P2：插件和模板机制

将渠道模板、审校规则、品牌规则和输出格式做成可注册组件。插件必须声明权限、输入输出 schema 和兼容版本，禁止插件直接访问数据库连接或任意文件。

## 4. 评测与科学性

### 4.1 现状与问题

现有测试能证明 API、状态流转、安全边界和异常路径基本可用，但不能回答以下问题：

- 新 Prompt 是否真的提高了文案质量？
- 审校 Agent 是否减少了人工修改？
- 反馈学习是否比不使用记忆更好？
- 成本增加后，质量提升是否值得？

### 4.2 建议方案

#### P0：建立固定评测集

先建立 30 条，再扩展到 100 条营销任务，覆盖不同渠道、行业、受众和限制条件。每条样本应包含：

- 输入主题、品牌、受众、渠道和禁用要求；
- 期望满足的硬约束；
- 人工参考答案或评分说明；
- 版本、模型、Prompt 和运行参数。

评测数据不得包含真实客户密钥、未授权品牌资料或个人信息。

#### P0：定义可重复评分维度

建议至少记录：

| 指标 | 含义 |
|---|---|
| Schema 通过率 | 输出是否能被严格解析 |
| 约束满足率 | 是否满足渠道长度、禁用词、品牌规则 |
| 事实一致性 | 是否引用或遵守输入中的事实 |
| 可用性评分 | 人工对标题、正文、行动号召的评分 |
| 修改率 | 人工定稿相对初稿的编辑比例 |
| 审校打回率 | review 节点首次通过/打回比例 |
| 成本与延迟 | 每任务 token、费用和耗时 |

LLM-as-judge 只能作为辅助指标，关键结论应保留人工抽样复核。

#### P0：建立回归门槛

每次修改 Prompt、模型或节点逻辑时，CI 至少检查：

- Schema 通过率不得下降；
- 硬约束满足率不得低于基线；
- 平均成本和延迟不能超过预算阈值；
- 关键样本不能出现严重安全或品牌合规回归。

#### P1：做消融实验

至少比较四组：

1. 无竞品分析；
2. 无审校循环；
3. 无品牌记忆；
4. 完整流水线。

用相同输入、模型和随机性设置比较质量、修改率、成本和延迟，才能证明每个 Agent 的实际价值。

## 5. 生产部署能力

### 5.1 现状与边界

当前 Docker、超时看门狗、启动恢复、并发信号量、限流和结构化日志对单机部署已经足够。但 SQLite checkpoint、进程内后台任务、内存限流和 SSE 连接都隐含“单实例”前提。

### 5.2 建议方案

#### P0：先补齐生产护栏

- 所有真实部署默认要求 `API_TOKEN`，启动时拒绝空 token；
- 增加 `/readyz`，区分进程存活、数据库可写和流水线可用；
- 为 LLM 调用增加指数退避、最大重试次数和总预算上限；
- 日志统一脱敏，禁止记录 Authorization、Prompt 中的秘密和完整用户输入；
- 增加优雅停机：停止接收新任务、等待有限时间、持久化运行状态。

#### P1：引入任务队列和持久化事件

将 API 请求、任务调度和 Agent 执行解耦。API 只创建任务并入队，worker 消费任务并写入事件表。SSE 从事件表或 Redis Stream 读取，而不是依赖某个进程内任务。

推荐迁移顺序：

1. 先定义 `task_events` 表和事件 schema；
2. 再把当前 `asyncio.create_task` 包装成可替换的 dispatcher；
3. 最后接入 Redis/RQ、Celery 或其他队列实现。

#### P1：替换单机共享状态

- 任务队列负责并发和重试；
- Redis 负责分布式限流、事件广播和短期锁；
- PostgreSQL 负责业务数据和 checkpoint；
- 对象存储负责大文档、附件和导出产物。

SQLite 仍可保留为本地 Demo 和测试后端，但应明确标注为单机模式。

#### P1：补充可观测性

每次任务和每个节点至少关联：`trace_id`、`task_id`、`node_id`、模型、Prompt 版本、耗时、token、重试次数和错误分类。优先采用 OpenTelemetry，并提供最小 Prometheus 指标：任务成功率、失败率、P95 延迟、每任务成本和队列长度。

验收标准：能够从一个失败任务定位到具体节点、模型请求、重试原因和最终状态，而不需要翻查多份非结构化日志。

#### P2：部署与灾备

- CI 中执行 Docker build 和容器健康检查；
- 增加数据库备份、恢复和迁移演练；
- 对 SSE 断线、worker 重启、重复消费和超时任务做集成测试；
- 明确 RPO/RTO，而不是笼统宣称“支持生产”。

## 6. GitHub 展示与社区成熟度

### 6.1 现状与问题

代码、测试、Docker 和 CI 已经具备，但访客需要自己阅读大量 README 才能理解价值。公开仓库还缺少能快速建立信任的结果证据和维护规则。

### 6.2 建议清单

#### P0：README 首屏

首屏应包含：

- 一句话定位；
- 真实 UI 截图或 30～60 秒 Demo GIF；
- CI 状态徽章；
- 本地 FakeLLM 一键启动命令；
- 真实模型与演示模式的差异；
- 明确的已知限制。

#### P1：可信证据

新增以下文档或章节：

- `docs/evaluation.md`：评测集、评分方法和基线结果；
- `docs/architecture.md`：数据流、状态机、失败恢复和部署边界；
- `SECURITY.md`：漏洞报告方式和敏感数据原则；
- `CONTRIBUTING.md`：开发环境、测试、提交规范和 PR 要求；
- `CHANGELOG.md` 或 GitHub Releases：版本变化和迁移说明。

#### P1：让 Demo 可验证

- 使用固定 FakeLLM 响应，保证每次演示一致；
- 提供一条命令启动前后端并执行 smoke test；
- 展示一次审校打回、人工编辑、反馈学习和再次生成；
- 所有截图和示例数据使用虚构品牌与主题。

#### P2：社区基础设施

- Issue 模板：Bug、功能建议、评测结果；
- Pull Request 模板：测试证据、兼容性、迁移影响；
- CODEOWNERS 和版本策略；
- 每月发布一份简短的 Roadmap 或实验结果；
- 对外公开已知限制，不把 MVP 能力描述成通用平台能力。

## 7. 推荐执行顺序

### 第一个迭代：建立证据

1. 建立 30 条评测集和评分脚本；
2. 在 CI 中加入 schema、硬约束和成本回归；
3. README 增加截图、Demo、CI 徽章和限制说明；
4. 增加 Docker build、health check 和最小 E2E。

### 第二个迭代：降低耦合

1. 抽象 LLM/Search Provider；
2. 为阶段输出增加版本化 schema；
3. 将流程节点和人工门配置化；
4. 增加第二个模型或 OpenAI-compatible provider。

### 第三个迭代：面向生产

1. 引入持久化事件表和 dispatcher；
2. 增加 OpenTelemetry、指标和脱敏日志；
3. 将限流、队列和事件广播迁移到 Redis；
4. 评估 PostgreSQL checkpoint 和多实例部署。

## 8. 完成定义

只有满足以下条件，才建议把项目从“垂直 MVP”升级描述为“生产可用平台”：

- 有公开评测集和至少一个可复现基线；
- 新增一个流程节点不需要修改核心 runner；
- worker 重启后任务能可靠恢复且不会重复产出；
- 两个实例同时运行时，限流、事件和任务状态仍然一致；
- CI 覆盖测试、构建、容器启动和关键 E2E；
- README、架构、评测、限制和安全文档完整；
- 所有对外性能或质量结论都有数据来源。

在达到这些门槛前，最准确的项目定位仍然是：

> 具备可恢复编排、人工审核和反馈学习能力的营销内容生产系统 MVP。
